# 从零开始学习清单：智能租房合同审查与租房全流程管理平台

> 目标读者：需要快速掌握本项目（项目汇报、技术总结、接手维护）的同学。
> 原则：**先跑起来，再读代码；顺着一条请求链路读，不要按文件列表死记**。
> 重要提醒：`README.md` 与 `docs/项目说明.md` 中部分描述已过时（例如"仅支持 TXT 解析""前端无测试"），本清单以当前代码为准。

---

## 0. 清单怎么用

- 全程建议 2~4 周：2 周是"密集版"（每天 4~6 小时），4 周是"标准版"（每天 2~3 小时）。
- 每个阶段都给了"产出/检查点"，做到能**自己讲出来**、**动手改一点**才算过关，光看懂不算。
- 学习顺序：跑起来 → 数据库 → 后端认证骨架 → 核心业务（合同审查/AI）→ 前端 → 测试部署。
- 所有文件路径均为项目内相对路径，根目录为项目根目录。

## 1. 阶段 0：把项目跑起来（第 1~2 天）

**目标**：本机能完整跑通"注册 → 登录 → 上传合同 → AI 审查 → 看报告 → AI 咨询 → 后台统计"。

**步骤**
1. 准备环境：JDK 21+、Maven 3.8+、Node.js 20+、MySQL 8.x、MinIO。
2. 初始化数据库：执行 `rental-platform-backend/sql/schema.sql`（建库 `rental_platform` + 9 张表）。
3. 启动顺序：MinIO（`start-minio.ps1`，API 9000 / 控制台 9001）→ 后端（`start-backend.ps1`，端口 8088）→ 前端（`start-frontend.ps1`，端口 5173）。
4. 打开 `http://localhost:5173` 注册一个普通账号，再注册/使用 `admin` 管理员账号登录，对比两种角色的菜单差异。
5. 上传一份 TXT/PDF/Word 租房合同，触发审查，看风险列表；再导出 PDF 报告。
6. 打开 `http://localhost:8088/doc.html`（Knife4j 接口文档），对着页面把常用接口点一遍。

**产出/检查点**
- 能说出三个启动脚本各自做了什么（读一遍 `start-backend.ps1`、`start-frontend.ps1`、`start-minio.ps1`）。
- 能复述"上传合同 → 审查"在页面上经历了哪几步。

## 3. 阶段 2：数据库层（第 3~4 天）

**目标**：把 9 张表的结构和关系装进脑子。

**要读的文件**
- `rental-platform-backend/sql/schema.sql`（唯一权威表结构）

**9 张表速记**

| 表 | 一句话作用 | 关键字段 |
| --- | --- | --- |
| `user` | 用户与角色 | `username`、`password`（BCrypt）、`role`、`status` |
| `contract` | 合同文件与审查结论 | `user_id`、`file_path`、`content`、`status`、`risk_level` |
| `review_record` | AI 审查出的每一条风险 | `contract_id`、`clause_content`、`risk_level`、`suggestion` |
| `house` | 房源 | `user_id`、`address`、`rent_price`、`status` |
| `house_viewing` | 看房记录 | `house_id`、`viewing_time`、`score` |
| `expense` | 水电燃气等费用 | `contract_id`、`expense_type`、`amount`、`is_paid` |
| `repair_request` | 维修报备 | `title`、`description`、`urgency`、`status` |
| `move_out_checklist` | 退租清单 | `contract_id`、`total_deposit`、`deduction_amount` |
| `ai_conversation` | AI 问答记录（多轮会话） | `user_id`、`question`、`answer`、`conversation_id` |

**通用设计**：`id` 自增主键；`created_at`/`updated_at` 自动填充（看 `MyBatisPlusConfig` 的 MetaObjectHandler）；业务表统一 `deleted` 逻辑删除。

**练习**
1. 写一条 SQL：查某用户所有合同及其风险数。
2. 手动插入一条合同数据，跑通"合同列表"接口看到它。
3. 画出 `user → contract → review_record` 与 `contract → expense/move_out_checklist` 的关系。

**产出/检查点**：能默写 9 张表及其关系；能解释"为什么审查结果单独建表而不是塞进 contract 一个大字段"。

## 4. 阶段 3：后端骨架与认证（第 4~6 天）

**目标**：掌握"一次请求从浏览器到数据库"的完整链路，以及权限模型。

**按这个顺序读**
1. 入口：`RentalApplication.java`；配置：`src/main/resources/application.yml`（端口、数据库、MinIO、DeepSeek、JWT）。
2. `common/Result.java`（统一返回体）→ `common/GlobalExceptionHandler.java`（统一异常）→ `common/PageResult.java`（分页返回）。
3. `common/JwtUtil.java`（签发/解析 token）→ `config/JwtAuthenticationFilter.java`（每次请求校验 token，把用户 ID 放进安全上下文）→ `config/SecurityConfig.java`（哪些接口放行、哪些必须登录、403/401 处理）。
4. `common/SecurityUtil.java`（`getCurrentUserId()`——所有归属校验的入口）。
5. 选一个最简单的模块精读"三层一接口"：`controller/UserController.java` → `service/UserServiceImpl.java` → `mapper/UserMapper.java`。

**认证流程串讲（要能自己讲）**
注册（BCrypt 加密密码）→ 登录（校验密码，签发 JWT，24 小时有效）→ 前端把 token 放 `Authorization: Bearer` → 过滤器校验并写入用户 ID → 业务层用 `SecurityUtil.getCurrentUserId()` 过滤数据 → token 缺失返回 401，越权返回 403。

**练习**
1. 在 UserController 里新增一个"仅本人可见"的接口（如返回当前用户合同数），完成归属校验。
2. 用 Knife4j 分别用"无 token / 普通用户 token / admin token"调管理接口，观察 401/403。
3. 说出 `@PreAuthorize("hasRole('ADMIN')")` 为什么能拦管理接口（JWT 里带角色声明 + `@EnableMethodSecurity`）。

**产出/检查点**：能画一次认证请求的时序；能说清"IDOR 越权"在本项目里怎么被防住的（每个按 ID 操作的接口都校验 `contract.getUserId().equals(currentUserId)`）。

## 5. 阶段 4：核心业务——合同审查与 AI（第 5~8 天）

**目标**：把项目最值钱的两条链路吃透。

### 5.1 合同审查链路
**文件**：`controller/ContractController.java` → `service/impl/ContractServiceImpl.java` → `service/impl/DeepSeekServiceImpl.java` → `config/MinioConfig.java`

链路：
```text
前端选文件 → POST /api/contract/upload
  → MinIO 存原文件（对象名 contracts/{userId}/{uuid}.ext）
  → PDFBox/POI 提取文本（TXT 直接读；PDF 用 PDFTextStripper；docx 读段落+表格；doc 用 HWPF）
  → 存 contract 表（status=pending）
→ POST /api/contract/review/{id}
  → 归属校验（不是本人合同直接报错）
  → DeepSeekServiceImpl.reviewContract(content)
      → 提示词：6 个审查维度（租金押金/租期续租/维修责任/违约对等/退租押金返还/其他）
      → 要求返回固定 JSON 数组：clauseContent/riskType/riskLevel/riskExplanation/suggestion/isHighRisk
      → temperature=0.3（审查要稳定）
  → 解析 JSON（extractJsonArray 容错提取）
  → 逐条存 review_record，汇总 riskLevel/riskCount 更新 contract
→ 前端 ContractReview.vue 展示风险卡片 + 等级标签 + 进度条
→ exportReviewReport 用 PDFBox + 中文字体（Deng.ttf/simhei/msyh）生成 PDF 报告
```

**要理解的关键点**
- 提示词工程是"AI 审查"的灵魂：结构化输出、维度约束、温度设置。
- `extractJsonArray` 是容错处理，但**解析失败时会静默返回空数组，合同被标记"低风险/0 条"**——这是本项目最值得讨论的可靠性问题。
- 合同文件同时在两处：MinIO（原件）+ MySQL `content` 字段（提取的文本）。

### 5.2 AI 顾问与会话管理
**文件**：`DeepSeekServiceImpl.chat/loadHistory/listConversations/getConversationMessages/deleteConversation`、`controller/AiController.java`、前端 `views/AiChat.vue`、`api/ai.js`

- 多轮对话：系统提示词 + 该会话**最近 10 条**历史 + 新问题 → DeepSeek（temperature=0.7）→ 存 `ai_conversation`。
- 会话聚合：按 `conversation_id` 分组，首条问题前 30 字当标题，按最后时间倒序。
- 删除 = 按 `conversation_id` + `user_id` 物理删除。

**练习**
1. 上传一份真实租房合同，审查后对比"人工判断"和"AI 判断"的差异（这就是项目汇报里值得展示的对比验证法）。
2. 改 `buildReviewPrompt`：加一个"押金返还期限"专项维度，重跑审查，观察输出变化。
3. 故意把 DeepSeek 返回改成非法 JSON（可临时改代码模拟），观察系统行为，思考应不应该这么处理。

**产出/检查点**：能徒手画审查时序图；能讲清楚提示词里每个字段的作用；能说出 AI 输出不稳定时系统的兜底策略及其隐患。

## 9. 阶段 8：项目汇报口径（贯穿全程，最后 1~2 天集中）

**每个模块准备"一句话三要素"**：功能是什么 / 用什么技术 / 亮点或难点在哪。

示例口径：
- 合同审查：上传 PDF/Word/TXT，PDFBox/POI 解析文本，DeepSeek 按 6 维度返回结构化 JSON，入库后前端卡片展示、PDF 导出——难点是提示词设计与模型输出不稳定。
- 认证权限：JWT 无状态认证 + 方法级权限 + 按 userId 数据隔离，防止越权。
- AI 顾问：多轮会话（最近 10 条上下文）+ 会话列表/续聊/删除。
- 工程化：AOP 耗时日志、后端分页、MinIO 文件预览下载、21 个后端 + 8 个前端测试。

**高频汇报问题（提前想好答案）**
1. 为什么用 JWT 而不是 Session？（无状态、易扩展；缺点是无法主动失效）
2. 怎么防止越权访问别人的合同？（每个按 ID 接口都做归属校验 + 按 userId 查询）
3. AI 审查结果可信吗？（参考性质；6 维度提示词；temperature=0.3；解析失败兜底逻辑的隐患）
4. 为什么分页放在后端而不是前端 slice？（数据量大时前端全量拉取不现实）
5. MinIO 解决什么问题？（文件与数据库分离、对象存储、统一管理合同原件）
6. 项目最大的难点/你做了什么改进？（AI 结构化输出、历史会话、文件预览下载等均可）

## 11. 附：常见坑（学习时容易踩）

1. **文档过时**：README/项目说明里"仅 TXT、无前端测试、12 个用例"等描述与代码不一致，以代码为准。
2. **AI 审查解析失败静默降级**：DeepSeek 返回不规范时会被当作"无风险"，学习时可思考更好的兜底方案（报错或人工复核标记）。
3. **MinIO 没启动**：合同上传必失败，先 `start-minio.ps1`。
4. **DeepSeek Key 未配置**：`application.yml` 里 `DEEPSEEK_API_KEY` 为空会直接报错，用环境变量注入。
5. **JDK 版本**：本项目用 Java 21 开发；如用 JDK 24+ 跑测试，`pom.xml` 已配好 `argLine`，不要删。
6. **JWT 密钥 / CORS**：`application.yml` 的 `jwt.secret` 是开发用值，部署到公网必须更换；CORS 只放行 localhost:5173。
7. **OCR 未实现**：扫描版 PDF（图片）解析不了，汇报时如实说是"探索性规划"。
